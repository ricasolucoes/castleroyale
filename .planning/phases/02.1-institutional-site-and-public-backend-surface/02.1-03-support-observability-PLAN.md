# Plan 02.1-03: Support submission, observability and public-surface verification

## Goal

Provide a safe support path and prove the institutional surface cannot be used to
reach game or staff state.

## Requirements

- REQ-16
- REQ-12

## Tasks

<task>
<read_first>
- apps/api/routes/web.php
- apps/api/app/Http/Requests/
- apps/api/config/mail.php
- docs/security/rate-limits.md
- .planning/phases/02.1-institutional-site-and-public-backend-surface/02.1-CONTEXT.md
</read_first>
<action>
Add a named POST route `site.support.submit` with a dedicated form request that
accepts only `name`, `email`, `locale`, `subject` and `message`, validates lengths
and email format, and rejects unknown fields. Apply a limiter keyed by normalized
email plus client IP with a documented per-minute threshold. Send a notification to
the configured support recipient through the existing mail system, using a queued
delivery only if the queue path is already available; otherwise return a bounded
success/failure response. Never include passwords, access tokens, account ids,
world ids or raw request headers in mail or logs.
</action>
<acceptance_criteria>
- `SupportSubmissionTest` proves a valid request reaches the configured mail fake and returns the localized success state.
- Invalid email, oversized message and unknown field requests return validation errors without sending mail.
- Repeated requests over the documented limiter return HTTP 429 and do not send mail.
- Source and log assertions prove no token, password, account id or world id is included in the notification payload.
</acceptance_criteria>
</task>

Extend architecture and feature coverage so institutional controllers, requests,
notifications and views cannot import game-domain models or call gameplay command

`docs/operations/observability.md`.
</action>

- Observability documentation names the support success, validation, rate-limit and mail-failure signals and their operators' response.
</acceptance_criteria>
</task>
