# Phase 02.1: Institutional Site and Public Backend Surface - Context

**Gathered:** 2026-08-27
**Status:** Ready for planning
**Source:** User-requested scope addition, audited against the current Laravel app.
These decisions are locked for this phase.

<domain>
## Phase Boundary

The Laravel application serves a public institutional site for Castle Royale.
It explains the product, publishes legal/support content and provides a protected
support channel. It does not become a web game client and never reads or mutates
player-owned game state.

**Depends on:** Phase 01, Phase 02
**Milestone:** Foundation

This phase is complete when every success criterion in `.planning/ROADMAP.md`
(Phase 02.1) is demonstrably true.

**Planned work:**

1. Public Laravel layout, routes and localized page content.
2. Shared token-backed styles, accessibility, metadata, sitemap and robots.
3. Support submission, rate limiting, observability and feature verification.
</domain>

<decisions>
## Implementation Decisions

### One Laravel application, three surfaces
- Keep public web routes in `apps/api/routes/web.php` and server-rendered views in
  `apps/api/resources/views/`.
- Keep `/api/v1` contract-first and keep `/admin` staff-only; public web code must
  not import game domain models or call game commands.
- Use `config('game.name')`; never hardcode the product name in a view or route.

### Content and locales
- Initial public pages are home, game/features, support, privacy and terms.
- Support pt-BR, en and es using the existing localization conventions. Locale is
  selected from an allow-list and is request-scoped only.
- Version content in the repository. A CMS is explicitly deferred until a new ADR
  justifies it.

### Visual and accessibility contract
- Use the shared semantic tokens from `packages/tooling/design-tokens/index.ts`.
- Expose token values to Tailwind/CSS through a generated or checked-in CSS token
  artifact; views must consume semantic custom properties/classes, not literals.
- Meet keyboard navigation, visible focus, landmarks, headings, alt text and
  reduced-motion requirements. Do not invent a second visual language.

### Support safety
- Validate name, email, locale and message server-side; strip or reject unexpected
  fields and never accept account ids, world ids or game outcomes.
- Rate-limit by IP and normalized email. Do not persist secrets or player state.
- Mail delivery is best-effort and observable; local development uses Mailpit and a
  missing mail transport returns a safe user-facing failure without a stack trace.

### Non-negotiables
- The server owns game truth; this phase must not mutate game truth.
- No balance number, timestamp rule or player-owned value is added here.
- No public route can access a staff-only action or bypass authorization.
- No literal visual token values in institutional views or CSS outside the token
  artifact.

### Claude's Discretion
- Blade component names and the exact route/controller split.
- Whether the support delivery uses a queued notification or a synchronous mail
  adapter, provided the request remains bounded and the outcome is observable.
- Exact copy wording, provided the three locales are complete and no legal claim
  is invented without an owner review.
</decisions>
