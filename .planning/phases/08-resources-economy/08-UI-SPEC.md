## Data Contract Dependency (flagged for the planner, not decided here)

`08-05` cannot interpolate production between server reads without knowing the
current **rate**. Today's `CityResources` schema (`packages/contracts/openapi.yaml`)
only exposes `current` and `capacity` — no rate. This is the same class of gap
Phase 07's UI-SPEC flagged for `CitySlot`; it must land in **08-01** (which
already owns "production rates") before 08-05 can be built, not decided
retroactively by the client.

```yaml
CityResources:
  type: object
  required: [current, capacity, rate]
  properties:
    current:
      $ref: '#/components/schemas/ResourceBundle'
    capacity:
      $ref: '#/components/schemas/ResourceBundle'
    rate:
      $ref: '#/components/schemas/ResourceRate'

ResourceRate:
  type: object
  description: >-
    Net production, integer units per hour, signed. Positive accrues toward
    capacity. A future negative value (upkeep, Phase 12) would drain toward
    zero — the sign is supported now so this contract does not need a rewrite
    later, even though every rate is >= 0 until Phase 12 ships upkeep.
    Display-only: the client never uses this figure as the basis of an
    affordability check (CONTEXT.md, Client decision) — only `current` read
    fresh from the server governs what can be spent.
  additionalProperties: false
  properties:
    food: { type: integer }
    wood: { type: integer }
    stone: { type: integer }
    iron: { type: integer }
    gold: { type: integer }
```

`CityData.server_time` (already required on `CityData`) remains the "as-of"
instant for these figures — no new timestamp field is needed; the client pairs
`rate`/`current`/`capacity` with `dataUpdatedAt` (see Interpolation Contract).

**Assumed unit: integer per hour.** `docs/game-design/economy.md` already
uses hourly as the economy's natural vocabulary ("Troops consume food per
hour"), and `packages/game-data/data/buildings.json`'s `production.food add 1`
values are small enough to only make sense as an hourly figure, not per-second
or per-tick. This is a genuine assumption for 08-01's implementer to confirm,
not something a UI contract can settle — flagging it here so 08-01 and 08-05
agree on the wire unit before either is built.

## Component, Interaction & Interpolation Contract

*(Supplementary to the template — required because the roadmap deliverable is
a live, ticking HUD element governed by an explicit anti-lying constraint, not
a static screen.)*

### Placement: persistent across all five tabs, not scoped to the city screen

The roadmap calls it "the mobile resource bar," not "the city resource bar,"
and Phase 07's UI-SPEC already named `surface.raised`/`border.strong` for "the
resource header bar" as a thing the city screen would eventually hand off to.
Resources are a player-level concern, not a city-tab-only one — the bar
mounts once, above the tab navigator itself:

- Add `ResourceBar` as a sibling **above** `<Tabs>` in
  `apps/mobile/app/(tabs)/_layout.tsx`, wrapped in a `View style={{ flex: 1 }}`
  containing `<ResourceBar />` then `<Tabs>...</Tabs>`. `<Tabs>` keeps
  `flex: 1` and naturally receives whatever height remains — no manual pixel
  budget is computed or hardcoded anywhere for this.
- **Remove** the inline resource row from `CityScene.tsx` (the
  `RESOURCE_KEYS.map(...)` block and its `ResourceCounter` imports/usage). The
  global bar supersedes it; showing resources twice on one screen is not
  "persistent," it is duplicated and confusing.

### HUD-aware framing: satisfied by flex composition, not new pixel math

Per the project's game rules, HUD height must be measured at runtime, never a
hardcoded constant. In React Native, mounting the bar as a normal flex sibling
above `<Tabs>` (rather than as an absolutely-positioned overlay) satisfies this
by construction: the bar's height is whatever its own content needs
(icon+numeral row + meter row + safe-area padding — no fixed height is ever
set on it), and every tab screen automatically receives the true remaining
space through ordinary flexbox, not through a value anyone typed in.

This specifically does not break the two screens that already measure their
own frame at runtime:
- **World map** (Phase 06): `MapCanvas` measures its own container via
  `onLayout`; a smaller ambient container from the new bar is picked up
  automatically, no `MapCanvas` change needed.
- **City scene** (Phase 07): `CityScene`'s slot grid is **width**-driven
  (`computeSlotLayout(frameWidth, ...)`), not height-driven, and its outer
  `ScrollView` already handles overflow. The only change City Scene needs is
  removing its own `insets.top` addition (see next point) — its grid math is
  otherwise untouched.

**Safe-area ownership moves to the bar.** Today `CityScene` adds
`insets.top + theme.spacing.sm` to its own top padding because it renders
directly under the status bar. Once `ResourceBar` sits above it and applies
`useSafeAreaInsets().top` to *its own* top padding, the tab content underneath
is no longer under the status bar — `CityScene` must drop its `insets.top`
term (keep the `theme.spacing.sm` gutter alone) or the top inset is double-
counted and the scene gets an unwanted gap. This is the one required edit to
`CityScene.tsx` beyond removing the resource row.

**Manual verification (no automated screenshot tool exists in this RN app
yet):** before marking 08-05 done, take one screenshot each of the city tab
and the world tab on a mid-range-equivalent simulator/emulator in portrait, and
confirm neither the slot grid nor the map canvas is clipped or pushed off the
bottom edge by the new bar. This is the project's standing "confira com
captura de tela antes de dar por pronto" rule, adapted to this stack since
`tools/shot.gd` is PlayTable/Godot-specific and does not exist here.

### Layout of the bar itself

```
┌───────────────────────────────────────────────────────────┐  ← insets.top + xs padding
│ [🌾 240]   [🌲 1.1K]   [⛰ 640]   [⚒ 90]   [🪙 2.4K]        │  row 1: icon + numeric, gap xs
│ ▓▓▓▓░░░░   ▓▓▓▓▓▓▓▓   ▓▓░░░░░░  ▓▓▓▓▓▓▓▓  ▓▓▓░░░░░         │  row 2: 4pt capacity meter
└───────────────────────────────────────────────────────────┘  ← border.strong bottom divider
```

- Outer container: `flexDirection: row`, `justifyContent: space-between`,
  `paddingTop: insets.top + theme.spacing.xs`, `paddingBottom: theme.spacing.xs`,
  `paddingHorizontal: theme.spacing.sm`, `backgroundColor: surface.raised`,
  `borderBottomWidth: 1`, `borderBottomColor: border.strong`. No fixed height.
- Five resource cells, each `flex: 1`, `gap: theme.spacing.xs` between cells.
- Each cell is built from the **extended** `ResourceCounter`:
  - Row 1 (existing behaviour, unchanged): `icon` (the resource-type glyph,
    16pt, tinted `resourceColors[resource]`) + `numeric`-variant amount text.
  - Row 2 (new): a `theme.spacing.xs`-tall (4pt), full-cell-width,
    `radius.full` track (`border.subtle` background) with an inner fill `View`
    whose width is `${percent}%` (`resourceColors[resource]` background),
    where `percent = capacity > 0 ? clamp(0, 100, (amount / capacity) * 100) : 0`.
  - When `isFull` (amount >= capacity): append a 12pt `tray-alert` glyph
    (`text.secondary`) immediately after the numeral, and render
    `resources.storage_full_short` ("MAX") as a `caption`-variant,
    `text.secondary` label beneath row 1. The meter fill still renders at
    100% width in the resource's own colour — never `danger`/red.
- `accessible={true}` on each cell with `accessibilityLabel` built from
  `resources.accessible_reading` (normal) or `resources.accessible_full`
  (at cap) — **no** `accessibilityRole="button"`, since nothing here is
  tappable and telling a screen-reader user otherwise would be a lie of a
  different kind.
- The outer bar container carries `accessibilityLabel={t('resources.bar_accessibility')}`
  as a landmark for screen-reader users skimming past it.

### Interpolation contract — must never lie

**Rule 1 — the server always wins, immediately, with no easing.** On every
successful resolution of the `['game', 'city']` query (scheduled poll, pull-
to-refresh, or realtime-invalidation refetch), the interpolation baseline is
reset **instantly** to the exact server values — `current`, `capacity`,
`rate`, captured against `cityQuery.dataUpdatedAt` (TanStack Query's own
client-side "resolved at" timestamp; do not hand-roll a second `Date.now()`
capture). No animated reconciliation, no "ease to the corrected value." This
mirrors `Timer.tsx`'s existing precedent of plain, unanimated text updates,
and it is the simplest rule that is also always honest: the displayed number
is *exactly* server truth at the instant of every read, full stop.

**Rule 2 — between reads, extrapolate forward, never backward, always
clamped.** A local 1Hz interval (same cadence `Timer.tsx` already uses)
recomputes the displayed bundle via a pure function:

```ts
// apps/mobile/src/features/economy/interpolation/interpolateResources.ts
// Pure, unit-testable, no RN/React import — mirrors the convention already
// established by features/city/rendering/grid.ts.

export type ResourceSnapshot = {
  current: ResourceBundle;
  capacity: ResourceBundle;
  rate: ResourceRate; // signed, integer per hour
  capturedAt: number; // cityQuery.dataUpdatedAt
};

export function interpolateResources(
  snapshot: ResourceSnapshot,
  now: number,
): ResourceBundle {
  const elapsedMs = Math.max(0, now - snapshot.capturedAt); // never extrapolate backward
  const result = {} as ResourceBundle;
  for (const key of RESOURCE_KEYS) {
    const base = snapshot.current[key] ?? 0;
    const cap = snapshot.capacity[key] ?? 0;
    const ratePerMs = (snapshot.rate[key] ?? 0) / 3_600_000;
    const projected = base + ratePerMs * elapsedMs;
    result[key] = Math.floor(cap > 0 ? Math.max(0, Math.min(cap, projected)) : Math.max(0, projected));
  }
  return result;
}
```

The `Math.min(cap, ...)` clamp is what guarantees "never display more than
capacity" and is what makes a resource visually stop climbing the instant it
hits the cap — there is no separate "stop ticking" flag to maintain; the clamp
already saturates. `Math.max(0, ...)` is the equivalent floor for the day a
negative (upkeep) rate exists. Floating-point math inside this function is
**not** an ADR-010 violation: ADR-010 governs stored, authoritative economy
state on the server; this function is purely a client display projection that
is explicitly never fed into an affordability check (CONTEXT.md, Client
decision) and always floors to an integer before render.

**Rule 3 — "smoothly" means every second, not an animated digit-roll.** The
counter visibly advances once per second between polls (unlike today's
`ResourceCounter`, frozen until the next full refetch) — it does not mean an
odometer-style animated digit transition. An animated digit-roll is an
explicit non-goal for this phase: it is disproportionate motion-design work
for a backend-heavy phase, and `Timer.tsx` already sets the "plain text swap,
no animation" precedent this component follows.

**Rule 4 — connectivity loss freezes, it does not fabricate.** While
`cityQuery.data` exists but the query is in an error state (a poll or
realtime-triggered refetch failed), pause the 1Hz interval — stop calling
`interpolateResources` with a fresh `now` — and hold the last computed values
on screen at reduced opacity (see Copywriting Contract → Error state). Resume
ticking automatically the moment `cityQuery.isSuccess` is true again. Never
let the client extrapolate across a connectivity gap it cannot confirm the
server was actually accruing through.

**Rule 5 — app resume triggers a real read, not a stretched guess.** Wire
`focusManager.setEventListener` with React Native's `AppState` in
`apps/mobile/app/_layout.tsx` (new — no such wiring exists in this codebase
yet; this is the standard, documented TanStack Query recipe for React Native,
not a bespoke mechanism). Without it, TanStack Query's focus-based refetching
never fires on RN at all, and a player returning after minutes away would see
the bar silently free-run its extrapolation across a gap long enough to make
the projection meaningless. This is app-wide infrastructure (benefits every
query, not just city) and belongs in the root layout, not the economy feature.

### Data flow summary

1. `apps/mobile/src/features/city/api/useCityQuery.ts` (new — extracted from

2. `app/(tabs)/city.tsx` switches to `useCityQuery()`; `ResourceBar` also

   two.
3. `useCityRealtime` (Phase 07-04, unchanged) keeps invalidating
   `['game', 'city']` on `city.state_changed` — this is what makes a spend or
   completed upgrade correct the bar immediately rather than waiting up to 30s.
4. `ResourceBar` derives its `ResourceSnapshot` from `cityQuery.data.resources`
   + `cityQuery.dataUpdatedAt`, ticks it forward locally per Rules 1–5 above.

## Flagged Assumptions (autonomous mode — not blocking, confirm during planning)

1. **Production rate unit is assumed integer-per-hour, signed.** This must be
   confirmed by 08-01's implementation, not re-derived by 08-05. If 08-01
   settles on a different wire unit, only the divisor in
   `interpolateResources` changes — the contract's shape (a `ResourceRate`
   sibling to `current`/`capacity` on `CityResources`) still holds.
2. **The bar polls the full `/game/city` payload** rather than a dedicated
   resources-only endpoint. Acceptable for this phase's scope; flagged as a
   future Phase 38 optimization if it proves too heavy at real load.
3. **AppState/focusManager wiring is scoped into 08-05** even though it is
   app-wide infrastructure, because the "never lie across a backgrounding gap"
   requirement is meaningless without it. If the planner prefers this land as
   its own small task rather than inside 08-05, that is a planning-time split,
   not a contract change.
4. **The bar is non-interactive in this phase.** Any future tap-to-expand
   (a production breakdown, a "+12/hr" tooltip) needs its own UI-SPEC
   addendum when a phase actually builds that screen — most likely Phase 34
   or Phase 46 (Economy Balance Pass), neither of which exists yet.
5. **CityScene's own `insets.top` removal is treated as in-scope for 08-05**
   (a one-line change, coupled to where the bar now owns the safe area), not
   deferred — leaving it in place would double the top gap on every device
   with a notch/status bar, which is a visible regression, not a neutral
   no-op.
