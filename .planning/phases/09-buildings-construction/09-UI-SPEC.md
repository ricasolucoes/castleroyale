# Phase 09 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Deliverable this contract governs:** plan **09-05 — Mobile building detail, upgrade
flow and construction queue UI** only. Plans 09-01 through 09-04 (catalogue import,
queue/timer persistence, completion jobs, requirement evaluation) are backend-only
and have no visual surface; this document extends two already-approved surfaces
(`CitySlotDetailSheet.tsx` from Phase 07, `CitySlot.tsx`'s in-tile Timer from Phase
07) and adds exactly one new component (a construction-queue strip). No screen this
phase does not build — a technology tree, a training screen, a requirements/unlock
browser — is designed here.

**What changes and why:** Phase 07 shipped the city scene and its slot detail sheet
deliberately with **no call-to-action** (07-UI-SPEC.md, Flagged Assumption 1: "the
currently-committed `city.tsx` already wires an `/upgrade` mutation... This contract
assumes that CTA is removed when the screen becomes a scene, and reappears properly
in Phase 09-05"). That removed CTA — and its cost/duration copy, its max-level
badge, its per-building Card layout — came from a pre-Phase-07 MVP scaffold
(`git show 7ede28c^:apps/mobile/app/(tabs)/city.tsx`) that this contract restores
**coherently inside the sheet**, not by reinventing the interaction from scratch, per
this phase's binding constraint #4.

## Data Contract Dependency (flagged for the planner, not decided here)

This is the same class of gap Phase 07 flagged for `CitySlot` and Phase 08 flagged
for `CityResources.rate`. Two genuine gaps exist; 09-01/09-02/09-03 must close both
before 09-05 is buildable as scoped by the roadmap.

### 1. `CityData.construction` must become a queue, not a single value

The roadmap's own language is plural: *"The construction queue: what is building,
how long remains, queue slot limits."* CONTEXT.md confirms the backend already
supports **multiple concurrent orders per city** —
`BuildingUpgradeService::start()` (line 80–87) counts `ConstructionOrder` rows with
`completed_at IS NULL` across the **whole city** against
`config('game.limits.max_build_queue_slots')` (currently `4`), and only refuses a
**second order on the same building** via a separate `CITY_BUSY` check (line 89–97).
Two different buildings can legitimately be under construction at once today.

But `CityStateService::handle()` (line 100–105) still does:

```php
$constructionQuery->getQuery()->whereNull('completed_at')->orderBy('finishes_at');
$construction = $constructionQuery->first();   // ← only the soonest order, others silently dropped
```

and `CityData.construction` is declared `oneOf: [Construction, null]` — singular.
A city with three simultaneous upgrades in flight would show the mobile client only
one of them, with the other two invisible until they complete. This UI contract is
written **against the following required shape**, which 09-02/09-03 must ship:

```yaml
CityData:
  required: [player, world, city, resources, slots, constructions, queue_limit, realtime, server_time]
  properties:
    # `construction` (singular) is REMOVED, replaced by:
    constructions:
      type: array
      description: >-
        Every active order for this city (completed_at IS NULL), in the same
        order the server would complete them. Empty array, not null, when
        nothing is building — matches the "array always present, in full"
        convention CitySlot already established in Phase 07.
      items:
        $ref: '#/components/schemas/Construction'
    queue_limit:
      type: integer
      description: >-
        game.limits.max_build_queue_slots, echoed back so the client never
        hardcodes a structural limit (ADR-013's rule extended to config, not
        just game-data).
```

`Construction` itself needs one addition: `slot: string` (or the client resolves it
by matching `building_code` against `slots[].building.code`, which is unambiguous
today because a building code appears in at most one slot — but only for as long as
no two slots can hold the same building code; if that ever changes, `slot` must be
added explicitly to avoid a client-side guess). Confirm which of the two 09-01
settles on and use it consistently in `constructions[]` and the per-tile `isBuilding`
lookup described below.

**Call sites that must change** when this ships (found by grep, so the planner has a
checklist instead of a search task):

- `apps/mobile/src/features/city/components/CityScene.tsx` — `city.construction` → `city.constructions` (array), `isBuilding` becomes a `.some()` check across the array instead of an `===` on one value.
- `apps/mobile/src/features/city/components/CitySlotDetailSheet.tsx` — `construction` prop becomes "the one entry of `constructions` whose `building_code` matches this slot's building," resolved by the caller (`CityScene`), not inside the sheet.
- `apps/mobile/src/features/city/realtime/useCityRealtime.ts` — **no change**; it only invalidates the query key, never reads the shape.

### 2. `build_time_seconds` shown in the pre-upgrade preview does not match the duration the server will actually use in local development

`CityStateService::handle()` returns the **raw** catalogue duration for the preview:

```php
'build_time_seconds' => $next === null ? 0 : (int) ($next['build_time_seconds'] ?? 0),
```

but `BuildingUpgradeService::start()` divides that same raw duration by
`config('game.time_scale')` before computing `finishes_at`:

```php
$duration = intdiv($rawDuration, $timeScale);
```

In production `time_scale` is forced to `1` (per CONTEXT.md), so this never affects
players. In local development — the environment this screen will actually be
tested in, repeatedly — the sheet would show, say, "45 seconds" and then the Timer
that appears the instant the player taps Upgrade counts down from a few seconds
instead, because `time_scale` is not `1` there. This is a genuine backend
correctness gap, not a UI decision: **09-01/09-02 should apply the same
`intdiv($rawDuration, $timeScale)` in `CityStateService`'s preview as
`BuildingUpgradeService` already applies when starting the order**, so the number
the player reads before tapping is the number they actually get. Flagging it here
because it would otherwise surface as a confusing "the timer doesn't match what I
was shown" bug report during 09-05's own manual verification pass, not as a defect
anyone thinks to attribute to 09-01.

### 3. Minor — OpenAPI response list for the upgrade endpoint is incomplete

`ErrorCode::httpStatus()` maps `BuildingMaxLevel`, `BuildingRequirementsNotMet`,
`BuildQueueFull` and `CityBusy` to the `default => 400` branch, but
`/game/city/buildings/{code}/upgrade` in `openapi.yaml` only documents `401`, `409`
and `422`. The mobile client branches on `error.code` from the JSON body, never on
the HTTP status, so this does **not** block 09-05's implementation — but per
ADR-017 ("one contract both sides verify against"), 09-02 should add a documented
`400` response referencing these four codes so the contract stays honest. Noted for
completeness, not blocking.

**What is NOT a gap:** `CityBuilding.next_level_cost` and `CityBuilding.max_level`
already exist and are exactly what this phase needs for the cost/duration/afford
display — no schema change required for those. `level >= max_level` is a
client-computable check the sheet can make with data it already has today.

## Color

The 60/30/10 split below describes **this deliverable's two surfaces** (the
extended sheet CTA area, and the new queue strip). It extends, and does not
contradict, `docs/design-system/tokens.md`'s canonical token meanings — see the
note on `accent.bronze` below.

| Role | Token | Usage |
|------|-------|-------|
| Dominant (60%) | `surface.raised` | Sheet background (unchanged, inherited from `BottomSheet`); the queue strip's filled-pip fill |
| Secondary (30%) | `bg.sunken` / `border.subtle` | Empty queue pips (dashed border, sunken fill — **identical visual grammar to an empty build slot** from Phase 07, deliberately: an "empty queue slot" and an "empty build plot" are both "capacity waiting to be used," and reusing the exact same fill/border pairing teaches the player one visual rule instead of two) |
| Accent (10%) | `accent.bronze` | **Two uses, both consistent with `docs/design-system/tokens.md`'s canonical definition "Primary action":** (1) the enabled Upgrade button — this is the first phase in the project where a true primary economic action exists in this scene, so bronze finally fulfils the role the token was always documented for; Phase 07's screen-scoped note that bronze was "only for loading indicators" was true only because no primary action existed yet, not a rule against ever using it for one; (2) the queue pip's progress-fill bar, extending the same "bronze marks active, primary, in-progress work" logic already used for loading spinners project-wide |
| Accent (10%) | `accent.gold` | **Unchanged from Phase 07.** Still reserved only for the empty-build-slot "buildable" glyph. This phase does **not** reuse gold for empty queue pips — a free queue slot is not "something you can build," it is capacity, and blurring the two meanings would violate the "accent reserved for specific elements" rule |
| Insufficient / blocked state | `text.secondary` | The disabled-CTA label text, the per-resource shortfall glyph (`alert-circle-outline`) next to a cost chip that is short. **Never `danger`.** This directly extends Phase 08's established rule that a normal economic ceiling ("storage full") is not an error and is not red; "not enough resources yet" and "queue full right now" are the same category of normal, temporary, non-destructive gate — using `danger` here would also contradict the one meaning `danger` is licensed for project-wide ("destructive, defeat") |
| Destructive | `danger` | **Not used.** Starting an upgrade is not classified as a destructive action in this project's taxonomy (see Copywriting Contract → Destructive confirmation, below) |

**Explicitly NOT color-coded:** whether the CTA is available. The signal is the
button's **text changing** ("Upgrade" → "Not enough resources" → "Queue full", or
the button disappearing entirely behind a "Max level" badge) — three states with
three different labels and two different shapes (enabled solid bronze vs. disabled
outlined secondary vs. no button at all), never a single grey/colored button with
identical text. This is a stronger compliance with "never colour alone" than an
icon-plus-color pairing would be, because there is no reliance on colour as a
signal at any point in the decision.

**Building category icons — closing a latent gap, not introduced by this phase:**
`CitySlot.tsx` currently distinguishes building category with a binary ternary
(`category === 'core' ? 'castle' : 'sprout-outline'`), which was safe only while the
game-data catalogue held two buildings. 09-01 imports the full 18-building
catalogue (`docs/game-design/buildings.md`); every non-Palace, non-economy building
would silently render `sprout-outline`, breaking Phase 07's own "category is never
communicated by colour alone — always a distinct silhouette" rule the moment it
matters. See Assets, below, for the required replacement mapping.

## Component, Interaction & Copy-Precedence Contract

*(Supplementary to the template — required because the roadmap deliverable is a
stateful decision surface with a defined precedence between four disqualifying
conditions, not a static form, and hard constraints #2 and #3 require an exact,
auditable affordability rule.)*

### A. Sheet CTA area — precedence order (mutually exclusive, evaluated top to bottom)

Extends `CitySlotDetailSheet.tsx`'s existing occupied-branch (building name, level,
category badge, construction Timer when `showConstruction`). The new CTA area
renders **only when `building !== null`**, immediately below the existing content,
and its content depends on exactly one of five mutually exclusive states:

```ts
const isMax = building.level >= building.max_level;
const isThisBuildingBusy = showConstruction; // existing variable, unchanged meaning
const activeCount = city.constructions.length;       // post data-contract-fix shape
const queueFull = !isMax && !isThisBuildingBusy && activeCount >= city.queue_limit;
const shortfalls = RESOURCE_KEYS.filter(
  (r) => (building.next_level_cost[r] ?? 0) > (city.resources.current[r] ?? 0),
);
const affordable = shortfalls.length === 0;
```

| # | Condition | Rendered CTA area |
|---|-----------|--------------------|
| 1 | `isMax` | `Badge variant="neutral" label={t('building.max_level')}` — **no button at all**, exactly restoring the pre-Phase-07 scaffold's pattern. `errors.BUILDING_MAX_LEVEL` copy is a defensive fallback only, for the rare race where a second device already upgraded the building past this cached view between page loads |
| 2 | `isThisBuildingBusy` | **Unchanged from Phase 07** — the existing Timer only, no button. Adding a disabled "Upgrading..." button here would duplicate a fact the Timer already states unambiguously and risks looking like a second, contradictory affordance |
| 3 | `queueFull` | `Button variant="secondary" disabled title={t('building.queue_full')}` |
| 4 | `!affordable` | `Button variant="secondary" disabled title={t('building.cannot_afford')}`, plus each short resource's cost chip (see B, below) gets a trailing 12pt `alert-circle-outline` glyph, `color={theme.color.text.secondary}` |
| 5 | else | `Button variant="primary" title={t('building.upgrade')} onPress={() => upgrade.mutate(building.code)}` |

While the mutation is in flight (`upgrade.isPending`), state 5's button title
switches to `t('building.upgrading')` and `disabled` becomes `true` — no spinner
overlay, no `Button` component change; this is a pure prop swap from the caller,
consistent with the project's "extend, don't fork" precedent (Phase 08 extended
`ResourceCounter` with new *props*; this phase needs no new props on `Button` at
all).

**Affordability reads the server snapshot, never the interpolated bar (hard
constraint #3).** `city.resources.current` above is `cityQuery.data.resources.current`
— the last value TanStack Query resolved from `/game/city`, the exact same object
`ResourceBar` uses as its `interpolateResources` *baseline* before ticking it
forward locally. The sheet **must not** import `interpolateResources`, must not read
`ResourceBar`'s displayed/ticked state, and must not call `Date.now()` anywhere in
the affordability check. This is the same discipline Phase 08's contract already
mandated for the bar itself, now extended to this phase's own spend-gating logic —
the two components independently derive from the one shared query cache entry and
never talk to each other directly.

**What happens when the server disagrees anyway (hard constraint #3).** A local
"affordable" or "queue not full" read can go stale between the sheet rendering and
the tap landing (another device, a completed order freeing a slot, accrual ticking
past a threshold). On mutation error:

1. Render the inline error `Text` (Copywriting Contract, above) below the CTA — the
   sheet stays open, it is not dismissed.
2. Call `queryClient.invalidateQueries({ queryKey: ['game', 'city'] })` immediately,
   the same call `useCityRealtime` already makes on every server event — this
   refetches truth and re-runs the precedence table above against it, so the CTA
   itself visibly updates (e.g. flips from state 5 to state 3 if the server's
   BUILD_QUEUE_FULL reveals the local `queue_limit`/`activeCount` read was stale).
3. Never optimistically show the building as upgrading before the 201 response —
   this is exactly the "no server-authoritative action shown as confirmed" rule in
   `docs/mobile/architecture.md`.

### B. Cost and duration display (state 3, 4 and 5 all show this; state 1 does not)

Directly above the CTA area, render a cost row and a duration row, both reading
values `CityBuilding` already exposes — **no new field needed for this part**:

```ts
export function formatResourceCost(
  cost: Partial<Record<ResourceKey, number>>,
  resourceLabel: (r: ResourceKey) => string,
): string {
  const parts = RESOURCE_KEYS
    .filter((r) => (cost[r] ?? 0) > 0)
    .map((r) => `${resourceLabel(r)} ${formatResourceAmount(cost[r] ?? 0)}`);
  return parts.length > 0 ? parts.join(' · ') : ''; // building.no_cost handled by caller
}
```

This restores, verbatim in behaviour, the `formatCost` helper deleted with the old
card list (per binding constraint #4) — export it from
`apps/mobile/src/shared/components/ResourceCounter.tsx` beside the existing
`formatResourceAmount`, not as a private per-screen function this time, since the
sheet now needs it and a future screen (Phase 12's training queue is the obvious
next consumer) will too.

- **Cost row:** one chip per resource where `next_level_cost[resource] > 0`:
  `RESOURCE_ICONS[resource]` glyph (12pt) + `numeric`-variant amount, coloured
  `theme.resourceColors[resource]` — visually identical to a `ResourceCounter` cell
  at small scale, but rendered inline (not the full bordered card) since this is a
  preview, not the persistent HUD. If every resource is zero, render
  `t('building.no_cost')` as plain `caption` text instead (exact restoration of the
  old scaffold's empty-cost branch).
- **Duration row:** `Timer.formatDuration(building.build_time_seconds * 1000)`,
  rendered as static `numeric` text (not a live `Timer` — nothing is counting down
  yet). Reusing the exported `formatDuration` guarantees the pre-commit preview and
  the post-commit live countdown use the *identical* `HH:MM:SS` format, so a player
  never sees two different time notations for the same number.
- Wrap both rows in one `accessible` `View` with a combined `accessibilityLabel`
  built from `building.cost_accessible` + `building.duration_accessible` — screen
  reader users get one coherent announcement instead of reading icon-only chips.

### C. Construction queue strip (new component)

Placed in `CityScene.tsx`, between the city name/location header and the slot grid
— inside the existing outer `ScrollView`, so **no new HUD-framing math is needed**:
Phase 07's frame measurement is width-driven for the grid and the whole screen
already scrolls vertically for overflow (07-UI-SPEC.md § Slot grid sizing, step 5);
adding one more row to that same scrollable column is not a new framing concern.

```
┌─────────────────────────────────────────────┐
│ Construction queue      3 of 4 slots in use  │  label + caption, row, space-between
│ [🏰──────] [🌾───▓▓] [⚒▓▓▓▓▓▓] [   +   ]     │  44×44 pips, gap xs
└─────────────────────────────────────────────┘
```

- Rendered only when `city.queue_limit > 0` (always true today, but this guards
  against a future world/config with no build queue at all rather than assuming).
- Container: `accessibilityLabel={t('city.queue_accessibility', { active: city.constructions.length, max: city.queue_limit })}`, `flexDirection: 'row', flexWrap: 'wrap', gap: theme.spacing.xs`.
- Header row: `Text variant="label"` (`city.queue_title`) + `Text variant="caption" color={theme.color.text.secondary}` (`city.queue_slots` reusing the same interpolation values as the accessibility label — add this one additional key: `city.queue_slots` = same copy as `city.queue_accessibility` without the "Construction queue:" prefix, i.e. `"{active} of {max} slots in use"` / `"{active} de {max} vagas em uso"` / `"{active} de {max} espacios en uso"`, since the visible header text already supplies the "Construction queue" label and repeating it in the caption would be redundant on-screen even though the accessibility label needs it standalone).
- `city.queue_limit` filled/empty pips, in order, each 44×44pt:
  - **Filled** (index `< city.constructions.length`): `surface.raised` fill, `border.strong` solid edge, `radius.md`, the building's icon (see Assets, below — resolved via the same `BUILDING_ICONS[code]` map the slot tile now uses) centred at 16pt (`theme.spacing.lg`), plus a 4pt (`theme.spacing.xs`-tall) `radius.full` progress bar along the bottom inner edge: track `border.subtle`, fill `accent.bronze`, width `${percent}%` where `percent = clamp(0, 100, (now - startedAtMs) / (finishesAtMs - startedAtMs) * 100)`, recomputed on the same 1Hz interval `Timer.tsx` already uses (same cadence, same "plain update, no animated roll" motion policy Phase 08 Rule 3 established — this is not a new motion pattern). `accessibilityRole="button"`, `accessibilityLabel={t('city.queue_slot_accessible', { building: t(building.name_key) })}`, `onPress={() => selectSlot(theSlotHoldingThisBuilding)}` — tapping a queue pip jumps straight to that building's own detail sheet, reusing the existing `citySelectionStore` unchanged.
  - **Empty** (index `>= city.constructions.length`): `bg.sunken` fill, dashed `border.subtle` edge — the identical visual grammar Phase 07 gave an empty build slot, deliberately (see Color, above). No icon (an empty queue slot is not "buildable," so it does not borrow the gold glyph). `accessibilityElementsHidden` — the container's own label already states "N of M slots in use" once; four more VoiceOver nodes each announcing "queue slot available" is noise, not information, given the summary already exists at the container level.
- **State management:** no new Zustand store. The strip reads `city.constructions` and `city.queue_limit` straight from the already-fetched `CityData` (same TanStack Query cache `CityScene` already holds), and reuses `citySelectionStore.selectSlot` for the one interactive affordance. This follows `docs/mobile/architecture.md` § The state rule exactly — server state stays in the query cache, the only client state involved (which slot's sheet is open) was already client state before this phase touched it.

### D. Per-tile Timer — plumbing change only, no visual change

`CitySlot.tsx` and `CityScene.tsx` already render an in-tile `Timer` for a building
under construction (Phase 07, unchanged visual treatment). The only change this
phase makes to that path is the lookup powering `isBuilding`, once the data
contract above ships:

```ts
// Before (Phase 07, singular):
const isBuilding = slot.building !== null && city.construction?.building_code === slot.building.code;
// After (Phase 09, array):
const isBuilding = slot.building !== null && city.constructions.some((c) => c.building_code === slot.building.code);
```

Every slot with an active order now shows its own live timer simultaneously — up
to `queue_limit` tiles ticking at once — with no redesign of `CitySlot.tsx` itself.
This is what already satisfies "what is building, how long remains" at the
scene-glance level; the queue strip in C exists to additionally answer "how many
slots, of how many total" at a glance, without requiring the player to scan the
whole grid and count.

## Flagged Assumptions (autonomous mode — not blocking, confirm during planning)

1. **The `CityData.construction` → `constructions[]` + `queue_limit` schema change
   is assumed to land in 09-02/09-03**, matching where the roadmap already places
   "Construction queue, cost debit and timer persistence" and "Completion jobs...
   and the overdue reconciler." If the planner instead wants a thinner client-side
   workaround (e.g. a second endpoint call listing orders), the sheet/strip/tile
   contracts above still hold — only the data-fetching plumbing changes, not the
   visual or interaction contract.
2. **`Construction.slot` is not required in this contract's minimum schema** —
   resolution by matching `building_code` against `slots[].building.code` is
   assumed unambiguous (today, a building code appears in at most one occupied
   slot). If a future phase allows the same building code to occupy two slots
   (unlikely per the 18-building catalogue, but not something this UI contract can
   rule out), `Construction.slot` becomes required and the queue pip's `onPress`
   target changes from "find the slot by building code" to "use `slot` directly."
3. **The `time_scale` preview-vs-reality mismatch (Data Contract Dependency #2) is
   flagged as a 09-01/09-02 fix, not something 09-05 works around client-side.**
   The client has no reliable way to learn `time_scale` itself (it is a
   server-local config value, deliberately never exposed as a "cheat sheet" for
   client-side duration math, consistent with "the server owns the truth") — the
   only correct fix is the server returning an already-scaled preview.
4. **No confirmation dialog before spending resources** is a discretionary call
   (Copywriting Contract → Destructive confirmation) consistent with this
   project's existing taxonomy and the already-tested MVP scaffold. If the planner
   or a later playtest decides upgrades warrant a confirmation step (e.g. once
   costs become large enough that a mis-tap is painful), that is a new decision for
   whichever phase revisits it — most likely Phase 46 (Economy Balance Pass) once
   real costs replace the current placeholder values.
5. **The queue strip's progress-fill bar is a "nice to have" polish detail**, not
   load-bearing for any roadmap success criterion. If 09-05's implementer judges it
   out of budget, the pip may ship as a static filled icon with no progress bar (the
   per-tile `Timer` in the grid below already gives the precise remaining time) —
   but the pip's *tap target and accessibility label* are not optional, since they
   are what makes the strip an actual navigation aid rather than a decorative
   counter.
6. **`ConstructionOrder`'s completion-triggered removal from `constructions[]`** is
   assumed to happen the same way a completed building already disappears from
   `city.construction` today (i.e., `completeOverdueLocked` runs before the read,
   so a finished order is never returned as still-active) — this is existing,
   already-tested backend behaviour (`CityStateService::handle()` calls
   `$this->completion->completeOverdueLocked($city, $now)` before building the
   response), not a new mechanism 09-05 needs to design around.
