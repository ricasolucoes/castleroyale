# Phase 10 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Deliverable this contract governs:** plan **10-04 — Mobile technology tree screen
and detail view** only. Plans 10-01 through 10-03 (schema/import, cycle validator,
research queue/timers/effects) are backend-only and have no visual surface. This
document also extends one already-approved surface by exactly one element — a
single new button inside `CitySlotDetailSheet.tsx` (Phase 09) — because the tree has
no tab of its own and needs a real entry point (see Component Contract §A).

**The roadmap success criterion this exists to satisfy** (Phase 10, criterion 5):
*"The technology tree screen renders dependencies and shows locked, available,
in-progress and completed states distinctly."* Every design decision below is
argued back to this sentence, not to genre convention for its own sake.

## Data Contract Dependency (flagged for the planner, not decided here)

Same class of gap Phase 07 flagged for `CitySlot` and Phase 09 flagged for
`CityData.constructions[]`: **no `Technology` schema exists yet anywhere in
`packages/contracts/openapi.yaml`.** Only the three `ErrorCode` enum members
(`RESEARCH_IN_PROGRESS`, `TECHNOLOGY_LOCKED`, `TECHNOLOGY_MAX_LEVEL`) exist today.
10-01/10-02/10-03 must ship the following shape — mirroring `CityBuilding` /
`CitySlot` / `Construction`'s existing conventions exactly — for 10-04 to be
buildable as scoped:

```yaml
TechnologyEffect:
  type: object
  required: [target, operation, value]
  properties:
    target:
      type: string
      description: >-
        Dotted path, e.g. "production.food". Drives the localization key
        `technology.effect_target.{target with '.' replaced by '_'}` — see
        Copywriting Contract.
    operation:
      enum: [add, multiply]
    value:
      type: integer
      description: >-
        Integer permille for `multiply` (ADR-010), whole units for `add`. See
        Flagged Assumption 1 — the UI needs the *sign convention* documented,
        not just the type.

Technology:
  type: object
  required: [code, name_key, category, tier, level, max_level, next_level_cost, research_time_seconds, prerequisites, next_level_effects]
  properties:
    code: { type: string }
    name_key: { type: string, pattern: '^technology\.[a-z][a-z0-9_]*$' }
    category:
      enum: [economy, military, defense, logistics, construction, exploration, alliance, siege]
      description: The 8 categories docs/game-design/technology.md already defines.
    tier:
      type: integer
      minimum: 0
      description: >-
        Topological depth in the full dependency DAG (0 = no prerequisites),
        computed once by 10-02's cycle-free validator and stored — the client
        never re-derives graph structure just to lay out a screen. This is the
        single most load-bearing field in this contract; see Layout Strategy.
    level: { type: integer, minimum: 0, description: "0 if never researched." }
    max_level: { type: integer }
    next_level_cost: { $ref: '#/components/schemas/ResourceBundle' }
    research_time_seconds: { type: integer }
    prerequisites:
      type: array
      description: Every entry must be satisfied (researched level >= level) to unlock this technology.
      items:
        type: object
        required: [code, level]
        properties:
          code: { type: string }
          level: { type: integer }
    next_level_effects:
      type: array
      items: { $ref: '#/components/schemas/TechnologyEffect' }

ActiveResearch:
  type: object
  required: [technology_code, from_level, target_level, started_at, finishes_at]
  properties:
    technology_code: { type: string }
    from_level: { type: integer }
    target_level: { type: integer }
    started_at: { type: string, format: date-time }
    finishes_at: { type: string, format: date-time }

TechnologyData:
  type: object
  required: [technologies, active_research, server_time]
  properties:
    technologies:
      type: array
      description: >-
        The full catalogue, always present in full — the same "array always
        present" convention `CitySlot` established in Phase 07. Not paginated;
        this phase does not need to plan for a catalogue too large to fetch
        once (docs/game-design/technology.md names 8 categories, not hundreds
        of nodes).
      items: { $ref: '#/components/schemas/Technology' }
    active_research:
      oneOf:
        - $ref: '#/components/schemas/ActiveResearch'
        - type: 'null'
      description: At most one, per CONTEXT.md's "one research at a time per player."
    server_time: { type: string, format: date-time }
```

**Fetched from `GET /game/technology`, cached at query key `['game', 'technology']`**
— this mirrors the already-shipped `MilitaryData` / `/game/military` /
`['game', 'military']` pattern in `apps/mobile/app/(tabs)/military.tsx` exactly,
not a new fetching convention.

**Affordability still reads `CityData.resources.current`, not this endpoint.**
`TechnologyData` carries no resource balances of its own — the tree screen additionally
reads the already-warm `['game', 'city']` cache (populated by the tab shell's
`ResourceBar`) for `resources.current`, applying the identical "server snapshot,
never the interpolated bar" discipline `CitySlotDetailSheet` already enforces
(Phase 09, hard constraint #3). No new query is introduced for this; the cache is
already warm by the time a player can reach this screen (see Component Contract §A).

**What is NOT a gap:** the `effect` shape `{target, operation, value}` already
exists verbatim in `packages/game-data/schema/buildings.schema.json`'s `$defs.effect`
and `$defs.requirement` (`type: enum[building, technology, nobility, player_level]`)
— 10-01 has a directly reusable precedent for both the effect descriptor and the
prerequisite/requirement descriptor; neither needs to be invented from nothing.

## Layout Strategy — Rendering a Dependency DAG at Arm's Length

This is the actual design problem this phase exists to solve, so it gets its own
section rather than being folded into "Component Contract."

**Rejected: a free-pan/zoom 2D graph canvas** (the approach Phase 06 used for the
world map). A drawn node-and-edge graph needs real graph-layout math (avoiding edge
crossings, positioning for readability) *and* a custom two-axis gesture handler, on
top of the cycle-detector 10-02 already has to build. For a tree with 8 documented
categories — not thousands of world tiles — that investment buys nothing a phone
user can use better than the alternative below, and it reopens exactly the
"alignment on a 390pt-wide viewport" problem addressed below by leaning on it
instead of avoiding it.

### Primary visual anchor

**What the eye lands on first: the in-progress node, when one exists.** It is the
only card on the screen carrying a moving element (the 1 Hz progress bar) and the
only one tinted `accent.bronze`, and motion plus the reserved action colour beat
everything static around it. That is the correct focal point because it answers the
question a returning player actually has — *is something cooking, and how long?* —
before they decide anything else.

**When no research is running, the anchor is the category jump strip**, which sits
sticky at the top and is the widest continuous horizontal element on screen. That is
also correct: with nothing in flight, the player's question becomes *what can I
start?*, and the strip is the fastest route to the category they care about.

Nothing else competes for that role. The screen header is deliberately `heading`
rather than `display` (see Typography) partly so it does not — a 32px title would
pull the eye to a word the player already knows, having just tapped to get here.

**Chosen: category sections stacked vertically, each containing horizontally-
scrolling tier lanes — the "Netflix-row" pattern, not a graph.**

```
┌ Research ────────────────────────────────────┐  ← header, back button, safe-area top inset
│ [Economy] [Military] [Defense] [Logistics] …  │  ← category jump strip, horizontal, sticky
│                                                │
│ Economy                                        │  ← section header: category icon + label
│  Tier 0  [Farming]  [Forestry]                │  ← horizontal lane, scrolls if it overflows
│  Tier 1  [Irrigation]                          │  ← lane below, only rendered if non-empty
│                                                │
│ Military                                       │
│  Tier 0  [Drill]  [Smithing]  [Fletching]  →  │  ← scrolls right, off-screen nodes still exist
│  Tier 2  [Siege Craft]                         │  ← tier 1 skipped silently — Military has none
└────────────────────────────────────────────────┘
```

1. **Outer container:** one vertical `ScrollView` — the whole page. Standard,
   already used by `CityScene` and `military.tsx` for exactly this reason: it is
   the one scroll axis every other screen in this app already relies on.
2. **One section per category**, in the fixed order docs/game-design/technology.md
   declares them (Economy, Military, Defense, Logistics, Construction,
   Exploration, Alliance, Siege) — a stable order the player learns once, not a
   dynamic sort. A category with zero technologies in the current dataset
   renders nothing (no empty section header for a category the dataset hasn't
   populated yet).
3. **Within a section, one horizontal lane per non-empty `tier` value present in
   that category**, ascending, skipping any tier with no nodes in that category
   silently (as in the Military example above). `tier` is the single global
   topological-depth field from the Data Contract, filtered to the category —
   this needs no second, category-local graph computation.
4. **A lane is a horizontal `ScrollView`**, `showsHorizontalScrollIndicator=false`,
   containing fixed-width node cards. **This is the one design decision that makes
   the 390pt-viewport question go away entirely:** a tier's node count is never
   bounded by the screen width, because it is not wrapped or fit to the frame —
   it scrolls. Nesting a horizontal `ScrollView` inside a vertical one is a
   standard, gesture-conflict-free React Native pattern (the two scroll views pan
   on orthogonal axes; RN's native scroll responder chain resolves this without a
   custom `PanResponder` or gesture-handler configuration), unlike a 2D pan+zoom
   canvas, which does need one. Nothing here requires Skia.
5. **Dependencies are rendered at three depths, deliberately, because no single
   mechanism can carry all of it on a phone without arrows:**
   - **Coarse (free):** stacking a category's tiers top-to-bottom already encodes
     "tier 1 requires something in tier 0" structurally, for free, from the layout
     itself.
   - **Medium (on the card):** any node at `tier > 0` shows a one-line, truncated
     caption under its name: `→ {first prerequisite's name}` (+`N more` if there is
     more than one), verified glyph `arrow-right-thin`, `text.secondary`. This is
     the "indented list with prerequisite chips" strategy, compressed onto the
     card itself rather than a separate list, because the card is already the unit
     the player scans.
   - **Full (in the sheet):** tapping any node opens its detail sheet, which lists
     **every** prerequisite as a chip — `{name} · {category label}` — because a
     prerequisite can legitimately live in a *different* category section (the DAG
     is not partitioned by category; nothing in CONTEXT.md or
     docs/game-design/technology.md forbids a Military tech requiring an Economy
     one). The category label on the chip is what lets the player actually go find
     it — this is the honest, phone-appropriate substitute for a drawn arrow
     crossing section boundaries, which no layout without a full graph canvas can
     draw anyway.
6. **Category jump strip** (header, sticky under the back button row): a horizontal
   row of 8 chips, icon + label, tapping one calls `scrollTo` on the outer
   `ScrollView` using that section's `onLayout`-measured `y` offset. This is
   navigation convenience only — nothing is hidden or filtered, so there is no
   "did my other techs disappear" confusion. See Flagged Assumption 4 for the one
   piece of this (highlighting *which* chip is currently in view while scrolling)
   that is genuinely optional polish.

   **Each chip is a 44×44pt minimum touch target**, met by an explicit
   `minHeight: theme.minTouchTarget` plus `hitSlop` where the visual chip is
   shorter. `sm` (8pt) horizontal padding sizes the chip visually and is not a
   touch guarantee. This is stated because `__tests__/touch-targets.test.tsx`
   exercises `Button` and `BottomSheet` directly — it will NOT catch an
   undersized bespoke `Pressable` built for this screen, so the obligation has to
   live in the contract instead of relying on the existing test to find it.

## Spacing Scale

Inherited verbatim from `docs/design-system/tokens.md` (locked Phase 02):

| Token | Value | Usage in this deliverable |
|-------|-------|----------------------------|
| `xs` | 4pt | Gap between stacked tier lanes within one category, node card's internal icon↔label gap |
| `sm` | 8pt | Gap between node cards in a lane, gap between a section header and its first lane, category-jump-chip horizontal padding |
| `md` | 12pt | Detail sheet section spacing (unchanged from Phase 07/09) |
| `lg` | 16pt | Sheet outer padding (unchanged), gap between category sections |
| `xl` | 24pt | Node card's category icon size (matches `CitySlot`'s tile icon size exactly — same visual weight for "a thing you can act on") |

**Node card footprint** (not a raw literal — a token expression, matching the
precedent `BottomSheet`'s `${theme.spacing['3xl'] * 4}%` snap point already sets
for "token arithmetic is fine, a bare number is not"):

- Width: `theme.spacing['3xl'] * 2` = 96pt
- Height: `theme.spacing['3xl'] * 2 + theme.spacing.xl` = 120pt

**Exception (inherited, not new):** every tappable element's hit area is a minimum
of `theme.minTouchTarget` (44pt) regardless of rendered visual size. Every node
card (96×120pt) clears this on both axes already; the header's icon-only back
button does not and needs the same `hitSlop` compensation `CitySlot`'s empty-plot
tile already uses.

## Typography

Inherited verbatim from `docs/design-system/tokens.md` (locked Phase 02):

| Role | Size | Weight | Line Height | Use in this deliverable |
|------|------|--------|-------------|--------------------------|
| `heading` | 18px | 600 | 24px | Screen header ("Research"), category section header, detail sheet's technology name |
| `numeric` | 16px | 600 | 20px (tabular) | Cost-chip amounts, static duration preview, in-progress node's live remaining-time text — reuses `Timer`/`formatDuration`, identical tabular figures |
| `label` | 14px | 500 | 20px | Node card name, category jump-chip label, CTA button text (via `Button`, unchanged) |
| `caption` | 12px | 400 | 16px | Node card's "→ prerequisite" hint, level pip text, requires-chip text in the sheet |

No new typography role is introduced, and this screen declares **four** sizes.

**Why the screen header is `heading` and not `display`.** `military.tsx` titles
itself with `display` (32px), and copying that would have made five sizes on one
screen. Phase 07 hit the same fork for the city screen and narrowed to four; this
follows that precedent rather than re-litigating it. `heading` is additionally the
better fit here: this screen's job is dense comparison across many small nodes, and
a 32px title spends vertical space that the first tier lane needs more. It also
matches the detail sheet's own `heading` treatment of a technology name, so the
same role reads as "names a thing" in both surfaces.

## Color

The 60/30/10 split below describes this deliverable's two surfaces (the tree
screen and its detail sheet). It extends, and does not contradict,
`docs/design-system/tokens.md`'s canonical token meanings, and it deliberately
does **not** reopen `accent.gold`'s narrow reservation from Phase 07/09.

| Role | Token | Usage |
|------|-------|-------|
| Dominant (60%) | `bg.base` | Screen background (matches every other screen) |
| Secondary (30%) | `surface.raised` / `bg.sunken` + `border.subtle` dashed | Node card fill for available/in-progress/completed states (`surface.raised`, solid `border.strong`); locked node card fill (`bg.sunken`, dashed `border.subtle`) — **the identical visual grammar `CitySlot` gives an empty plot and `ConstructionQueueStrip` gives an empty pip**, reused deliberately: "not yet actionable" is one visual rule in this app, not three |
| Accent (10%) | `accent.bronze` | **Two uses, both direct extensions of the rule Phase 09 established ("primary action / active work in progress"), not a new meaning:** (1) the enabled "Research" button; (2) the in-progress node's corner badge fill and bottom progress bar |
| Confirmation | `success` | The completed/max-level node's corner badge fill only. This is the **first** use of `success` in a building/technology context in this project (it is already used elsewhere for status badges — `military.tsx`'s "server sync" and `profile.tsx`'s "active" — but never yet to mark a piece of player progression as permanently done) — it is a direct, unforced fit for tokens.md's own canonical definition, "Confirmation, victory," applied to a technology that is now permanently, successfully done |
| **Explicitly not used** | `accent.gold` | Deliberately excluded. Phase 09 reserved gold *only* for the empty-build-slot "buildable" glyph; extending it here to mean "available technology" would blur that narrow reservation the same way reusing it for an empty queue pip would have (09-UI-SPEC's own reasoning, applied again here) |
| Insufficient / blocked state | `text.secondary` | "Locked" and "Not enough resources" and "Research in progress" disabled-button labels, the requires-caption text, the lock badge's glyph and ring. **Never `danger`** — same rule Phase 09 already proved: a normal, temporary, resolvable-by-playing-more gate is not an error |
| Destructive | `danger` | **Not used.** Starting research is not classified as destructive in this project's taxonomy — see Copywriting Contract → Destructive confirmation |

**Category icons are always `text.secondary`**, at every node state, with no
opacity trick layered on top — this matches `CitySlot`'s and
`ConstructionQueueStrip`'s existing rule (category/building glyphs are always
`text.secondary`) exactly, rather than inventing a new "dimmed" treatment that
would require a value this project has no opacity token for. **State is carried
entirely by border style (dashed vs. solid) and corner-badge shape/presence —
never by recoloring or dimming the icon** — see Component Contract §C for the
complete, exhaustive state table.

## Component, Interaction & Copy-Precedence Contract

### A. Entry point — one new button inside `CitySlotDetailSheet.tsx`

The tree has **no tab of its own.** `packages/localization/locales/en/navigation.json`
lists exactly five tabs (city, world, military, alliance, profile) and Phase 02's
already-passed, already-tested success criterion fixed that shell; adding a sixth
tab is out of scope for this phase and not requested by the roadmap. Per
docs/game-design/buildings.md ("Academy | Research"), the Academy building is the
thematic and mechanical front door.

Extend `CitySlotDetailSheet.tsx`'s existing occupied branch: when
`building.code === 'academy'`, render one additional `Button` **below** the
existing five-state upgrade CTA (Phase 09's block is untouched):

```tsx
{building.code === 'academy' && (
  <Button
    variant="secondary"
    title={t('city.open_research')}
    onPress={() => router.push('/technology')}
  />
)}
```

No accessibility-label override needed — "Open Research" is already
self-describing as visible text, unlike Phase 09's "Upgrade" which needed the
building's name appended for a screen-reader user landing on it out of context.

This button is present at every Academy level (research does not require any
particular Academy level in the data seen so far — that is a 10-01 game-data
decision, not a navigation one) and is simply **absent** for every other building,
including on a city that has not built an Academy at all yet — consistent with how
every other building-gated capability in this game today has no separate "you need
an X" banner anywhere else on the City screen.

### B. Screen: `apps/mobile/app/technology.tsx` → `TechnologyTreeScreen`

A pushed, non-tab route — same placement pattern as `gallery.tsx` / `onboarding.tsx`
(top-level under `app/`, not inside `(tabs)/`). `headerShown: false` is already the
global `Stack` default (`app/_layout.tsx`); this screen builds its own header row,
same as `military.tsx` and `gallery.tsx` already do with `useSafeAreaInsets()`.

```
┌ [←] Research                                   ┐  ← insets.top + spacing.lg padding
│ [Economy][Military][Defense][Logistics]…       │  ← category jump strip
│                                                 │
│ (scrollable body — see Layout Strategy)         │
└─────────────────────────────────────────────────┘
```

- Back control: icon-only `Pressable`, glyph `arrow-left` (verified), 44×44pt hit
  area via `hitSlop`, `accessibilityLabel={t('technology.back_accessible')}`,
  `onPress={() => router.back()}`.
- Header title: `Text variant="heading"` = `t('technology.tree_title')`. Deliberately
  NOT `display` — see Typography above; `military.tsx` uses `display` for its title
  but matching it would put five font sizes on this screen.
- Loading state: `Skeleton` blocks, same shape/count convention `military.tsx`
  already uses for its own `isPending` branch.
- Fetch-error state: reuses `errors.generic` / `errors.network` + a `common.retry`
  `Button`, identical to `military.tsx`'s existing `errorKey()` helper and error
  branch — no new copy needed for this path.

### C. `TechnologyNodeCard` — the four required states, by shape

Fixed 96×120pt (see Spacing Scale), `radius.md`, one `Pressable` per node,
`accessibilityRole="button"`, opens `TechnologyDetailSheet` for that `code` on tap
(selection lives in a new `technologySelectionStore` — client state, mirroring
`citySelectionStore` exactly per docs/mobile/architecture.md's state rule).

| State | Condition | Border | Corner badge (20pt circle, top-right) | Bottom edge |
|---|---|---|---|---|
| **Locked** | `tech.prerequisites.some(p => (levelOf(p.code) ?? 0) < p.level)` | dashed, `border.subtle`, fill `bg.sunken` | `lock-outline`, fill `surface.overlay`, ring `border.strong`, glyph `text.secondary` | none |
| **Available** | not locked, not maxed, not the active research | solid, `border.strong`, fill `surface.raised` | none | none |
| **In-progress** | `active_research?.technology_code === tech.code` | solid, `border.strong`, fill `surface.raised` | `progress-clock`, fill `accent.bronze`, glyph `text.inverse` | 4pt progress bar, track `border.subtle`, fill `accent.bronze` — identical mechanism to `ConstructionQueueStrip`'s pip, same 1Hz recompute cadence, same "plain update, no animated roll" policy |
| **Completed** | `tech.level >= tech.max_level` | solid, `border.strong`, fill `surface.raised` | `check-circle`, fill `success`, glyph `text.inverse` | none |

Every state pair differs in **at least one shape channel** (border style, badge
shape/presence, progress-bar presence), and most differ in two. The one pair that
differs in a single channel is **Available vs Completed**: both use a solid
`border.strong` and neither shows a progress bar, so the only distinction is the
corner badge — absent when available, a filled `check-circle` when completed.

That is still a *shape* distinction, not a colour one, which is what the
colourblind-safety rule requires: in a greyscale or bright-sunlight rendering the
badge is present or it is not, and presence reads at a glance. It is called out
here rather than smoothed over because a later phase adding a badge to the
available state would silently collapse the only channel separating these two —
if that happens, the available state must gain a distinct border treatment in the
same change.

The category icon itself never changes tint or opacity across states, so no state
is identified by colour at all.

**Why only four states, not six:** the roadmap criterion names exactly four —
locked, available, in-progress, completed. "Researchable but another research is
running" and "researchable but unaffordable right now" are real, but they are
transient *action* conditions, not identity states of the node — they surface one
tap deeper, in the sheet's CTA (§D), the same way Phase 09 kept "queue full" and
"cannot afford" out of `CitySlot`'s own four visual states and confined them to
`CitySlotDetailSheet`.

**Card content, top to bottom:** category icon (`theme.spacing.xl`, `text.secondary`,
from `technologyIcons.ts` — see Assets), name (`label`, 1 line, truncated), a small
level pip (`Badge variant="neutral"`, `"{level}/{max_level}"`, mirrors `CitySlot`'s
level badge), then exactly one of: the `→ {prerequisite}` caption (tier > 0,
not in-progress) **or** a live remaining-time `numeric` string via `Timer`
(in-progress only — the prerequisite hint is moot once the tech is already running).

### D. `TechnologyDetailSheet` — CTA precedence (mutually exclusive, evaluated top to bottom)

Directly extends the `BottomSheet` pattern `CitySlotDetailSheet` already
established — same component, unmodified, new content.

```ts
const isMax = tech.level >= tech.max_level;
const isThisTechActive = activeResearch?.technology_code === tech.code;
const isLocked = tech.prerequisites.some(
  (p) => (levelByCode.get(p.code) ?? 0) < p.level,
);
const busyElsewhere = activeResearch !== null && !isThisTechActive;
const shortfalls = RESOURCE_KEYS.filter(
  (r) => (tech.next_level_cost[r] ?? 0) > (city.resources.current[r] ?? 0),
);
const affordable = shortfalls.length === 0;
```

| # | Condition | Rendered CTA area |
|---|-----------|--------------------|
| 1 | `isMax` | `Badge variant="neutral" label={t('technology.max_level')}` — no button, exactly the `building.max_level` grammar |
| 2 | `isThisTechActive` | `Timer` only (targeting `activeResearch.finishes_at`, device-clock-skew-corrected identically to `Construction`'s timer), no button |
| 3 | `isLocked` | `Button variant="secondary" disabled title={t('technology.locked')}` — a *disabled button*, not a badge, because unlike "max level" this is resolvable by playing more (research the prerequisite), the same category of condition as "queue full"/"cannot afford" in Phase 09, not a permanent terminal state |
| 4 | `busyElsewhere` | `Button variant="secondary" disabled title={t('technology.busy')}` |
| 5 | `!affordable` | `Button variant="secondary" disabled title={t('technology.cannot_afford')}`, plus each short resource's cost chip gets the existing `COST_SHORTFALL_ICON` (`alert-circle-outline`), `text.secondary` |
| 6 | else | `Button variant="primary" title={t('technology.research')} accessibilityLabel={t('technology.research_accessible', { technology: t(tech.name_key) })} onPress={() => research.mutate(tech.code)}` |

While the mutation is in flight (`research.isPending`), state 6's title swaps to
`t('technology.researching')` and `disabled` becomes `true` — identical pattern to
Phase 09's `building.upgrading` swap, no new `Button` prop.

**Ordering rationale:** structural/terminal blockers (max, already-running-this-one,
locked-by-prerequisite) are checked before temporal/resource blockers (another
research running, insufficient funds) — a locked tech stays locked regardless of
whether the wallet is full or another research just finished, so it must win the
precedence check first.

**On mutation error** (server disagreed anyway): render the inline error `Text`
below the CTA (sheet stays open), then `queryClient.invalidateQueries({ queryKey:
['game', 'technology'] })` **and** `['game', 'city']` (a completed research may have
just changed `resources.rate`) — the same "refetch truth, never patch
optimistically" discipline `useUpgradeBuilding` already applies.

### E. Cost, duration, requires and effect display (states 3–6 show this; states 1–2 do not)

Above the CTA area:

- **Requires row** (only when `tech.prerequisites.length > 0`): one chip per
  prerequisite, `{name} · {category label}`, a small `check-circle-outline` glyph
  prefix when that prerequisite is already satisfied at the required level, no
  glyph otherwise — `text.secondary` throughout, never `success`/`danger` (this is
  informational, not a confirmation or a refusal).
- **Cost row:** identical mechanism to `CitySlotDetailSheet`'s — reuses
  `formatResourceCost` (already exported from `ResourceCounter.tsx`) and
  `RESOURCE_ICONS`, one chip per non-zero resource, `t('technology.no_cost')` when
  all are zero.
- **Duration row:** `Timer.formatDuration(tech.research_time_seconds * 1000)`,
  static `numeric` text — same exported helper, same `HH:MM:SS` format the live
  countdown will use once research actually starts.
- **Effect row** (recommended, not required by criterion 5 — see Flagged
  Assumption 1): one line per `next_level_effects` entry, `{signed amount}
  {t('technology.effect_target.' + target.replace(/\./g, '_'))}`. If the sign
  convention 10-01 ships does not match the assumption below, this row's exact
  text is wrong but nothing else in this contract breaks.
- Wrap requires + cost + duration + effect rows in one `accessible` `View` with a
  combined `accessibilityLabel`, same pattern `CitySlotDetailSheet` already uses.

## Flagged Assumptions (autonomous mode — not blocking, confirm during planning)

1. **The effect-description row's sign convention is assumed, not confirmed.**
   `docs/game-design/technology.md` says percentage effects are "integer permille,"
   but does not say whether a `multiply` operation's `value` is *the delta*
   (e.g. `value: 50` → "+5% production") or *the full multiplier in permille*
   (e.g. `value: 1050` → "×1.05"). This contract's formatter (§E) assumes the
   **delta** reading, because it is what "production rate rising by the documented
   amount" (roadmap criterion 4's own language) most naturally describes. If 10-01
   ships the other convention, only §E's arithmetic is wrong — nothing else in this
   contract (layout, states, precedence, colour) depends on it. This is the same
   category of gap 09-UI-SPEC flagged for `time_scale`: a backend semantic the UI
   cannot resolve by itself and should not guess silently.
2. **The tree's entry point is the Academy building's detail sheet, not a new tab
   or a persistent icon elsewhere.** This is a genuine placement decision no
   upstream artifact settled (the roadmap names the screen but not its entry
   point; CONTEXT.md is silent on navigation). Chosen for consistency with
   docs/game-design/buildings.md's own "Academy | Research" pairing and because
   Phase 02's five-tab shell is an already-tested, already-passed success
   criterion this phase has no mandate to reopen. If a later phase adds a
   dedicated Research tab, this button becomes redundant and can be removed
   without touching the tree screen itself.
3. **`tier` is assumed to be a server-computed, stored field**, not something
   10-04 derives client-side from `prerequisites[]`. This keeps a second
   graph-traversal implementation out of the mobile client entirely — the one
   already required in 10-02 (the cycle detector) is reused as the sole source of
   topological ordering. If the planner instead prefers the client to compute
   tiers itself from the raw `prerequisites[]` graph, the visual contract in this
   document (tier lanes, ascending, empty tiers skipped) is unchanged — only where
   the tier number comes from changes.
4. **Highlighting which category chip is "currently in view" while scrolling** is
   optional polish, not load-bearing for criterion 5. The jump strip's tap-to-
   scroll behaviour is required (it is the only way to navigate 8 sections
   quickly); tracking scroll position to bold the active chip is a nice-to-have
   that may ship as a static, unhighlighted strip if out of budget — the same
   class of trade-off Phase 09 flagged for its queue-pip progress bar.
5. **No cancel/refund affordance for an in-progress research** is out of scope —
   the roadmap's Phase 10 success criteria name locked/max/in-progress/one-at-a-
   time/observable-effect, never cancellation (unlike Phase 12's training queue,
   which explicitly lists "Cancellation, refunds" as its own success criterion).
   State 2 in §D (`Timer` only, no button) is therefore correct as the terminal
   in-progress treatment for this phase, not an oversight.
