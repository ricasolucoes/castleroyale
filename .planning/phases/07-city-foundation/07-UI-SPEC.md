# Phase 07 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Deliverable this contract governs:** the city screen (`app/(tabs)/city.tsx`) — a
spatial scene of addressable building slots, tappable, not a scrolling list of
cards. Ambience, particles and animation are Phase 44's job; this contract only
locks the structure Phase 44 must be able to decorate without a rewrite.

## Color

The 60/30/10 split below describes **this screen specifically**, drawn entirely
from the existing token set in `docs/design-system/tokens.md` — no new colour
token is introduced.

| Role | Token | Usage |
|------|-------|-------|
| Dominant (60%) | `bg.sunken` | The scene frame background (the "ground" the slots sit on), matching the treatment `MapCanvas` already gives its canvas background |
| Secondary (30%) | `surface.raised` / `border.strong` | Occupied-slot tiles, the resource header bar, the bottom sheet surface |
| Accent (10%) | `accent.bronze` | **Only** for busy/loading indicators: the initial `ActivityIndicator` and the `RefreshControl` tint — this matches the existing, established convention (`city.tsx`, `profile.tsx`, `LoginScreen.tsx` all use `accent.bronze` for spinners, never for retry buttons) |
| Accent (10%) | `accent.gold` | **Only** for the empty-slot "buildable" glyph — the one visual cue that a plot is available. Reuses gold's documented purpose ("Rarity, highlight") |
| Destructive | `danger` | Not used in this phase — no destructive action exists in City Foundation (no demolish/abandon flow). Reserved for a later phase |

**Explicitly NOT color-coded:** building category (`core`, `economy`, and
whatever Phase 09 adds later). Two reasons: (1) accent tokens are scarce by
design and category will grow to 5–6 values, which would force reuse of accent
hues for a non-accent purpose; (2) `docs/design-system/tokens.md` already commits
this project to never communicating state by colour alone (see rarity colours).
Category is instead communicated by **icon shape** + the `category` text on the
detail sheet — colourblind-safe by construction.

Retry / refresh **buttons** (as opposed to spinners) use `variant="secondary"` on
the existing `Button` component, exactly like every other screen in the app
(`city.tsx`, `world.tsx`, `military.tsx`, `alliance.tsx`, `WorldTileDetailSheet`
all do this already — `accent.bronze` is never used on a retry button anywhere in
the codebase, and this phase does not break that pattern).

## Scene, Layout & Interaction Contract

*(Supplementary to the template — required for this phase because the
success criteria mandate a spatial scene, not a form, and the project's game
rules in `/Users/sierra/Dev/Jogos/CLAUDE.md` are hard constraints, not
suggestions.)*

### Rendering approach: plain React Native views, not Skia

Unlike the world map (`MapCanvas.tsx`), the city scene renders as **ordinary
React Native components** (`View`/`Pressable`), not a Skia canvas. This follows
`docs/mobile/architecture.md` § Rendering directly: *"Ordinary UI is React
Native components. The world map, battle replay and particles are Skia."* A
city has, at most, a few dozen slots — nowhere near the "thousands of entities"
threshold that forced Skia batching on the map. Using RN `Pressable` per slot
also means:

- Native accessibility (VoiceOver/TalkBack) for free — no custom hit-testing.
- Real focus order and `accessibilityRole="button"` semantics, which the map's
  manual Skia tap math could not offer.

This does **not** contradict the game guideline against "a flat 2D grid
anchored to the screen over a 3D board": that rule targets scenes rendered with
a 3D/perspective camera, where a screen-space grid and world-space geometry
diverge. The city scene has no 3D camera and no perspective — it is flat by
construction, so a flat RN grid positioned by the same layout math that paints
it **is** the scene; there is no second, disconnected coordinate system to
misalign.

**Forward compatibility with Phase 44:** ambience and particles are Skia's job
per `docs/mobile/architecture.md`. Phase 44 adds a `Canvas` layer *behind or
around* this same measured frame (identical width/height/origin the grid
already computes) for background effects — it never needs to touch slot
positions or tap handling, because those stay in the RN layer. No rewrite.

### HUD-aware framing (mandatory, not optional)

Per the project's game rules, the scene must consume its own frame size
measured at runtime, never a hardcoded pixel budget:

- Frame height = `Dimensions` height − `useSafeAreaInsets().top` − the resource
  header's own measured height (`onLayout`) − the tab bar's rendered height
  (already known to Expo Router's `Tabs`; do not re-guess it as a constant).
- Frame width = full screen width minus at most `theme.spacing.sm` (8pt) of
  outer gutter per side — the ≈4% max-margin rule from the game guidelines.
  The scene is edge-to-edge, not a card floating in whitespace.
- Recompute on every relevant layout event (rotation, tab bar height change,
  font-scale change) — never assume portrait or a fixed device size.

### Slot grid sizing (data-driven, never a hardcoded count)

The number of slots comes from the server and **must never be hardcoded** on
the client (today's starter city has 5; the roadmap's building catalogue grows
to 18) — this is a direct extension of "the server owns the truth."

Algorithm the executor must implement:

1. `columns = max(1, floor(frameWidth / theme.spacing['3xl']))` — `3xl` (48pt)
   is the baseline tile unit, itself a token, not a magic number.
2. `tileSize = frameWidth / columns` — this fills the frame edge-to-edge with
   no leftover gap on either side.
3. If `tileSize < theme.minTouchTarget` (44pt), decrement `columns` by 1 and
   recompute until `tileSize >= 44` or `columns === 1`.
4. Slots fill rows top-to-bottom in the order the server returns them (stable
   `slot` identity — never re-sorted client-side).
5. If total row height exceeds the available frame height, the **outer**
   container becomes the vertical scroll region (see pull-to-refresh below).
   Horizontal scrolling is never introduced.

This produces a courtyard-like grid that reads as a "scene" (contiguous plots)
rather than a card list, satisfies the touch-target floor, and requires no
redesign when the slot count changes in a later phase.

### Slot visual states

| State | Visual treatment | Tap behaviour |
|-------|-------------------|----------------|
| Empty | `bg.sunken` fill, dashed `border.subtle` edge, centred `accent.gold` "available" glyph (e.g. `plus-circle-outline` from MaterialCommunityIcons) | Opens the detail sheet with `city.slot_empty` / `city.slot_empty_hint`. No button — informational only |
| Occupied | `surface.raised` fill, solid `border.strong` edge, a category icon (see Assets below), a `label`-weight building name, a small `caption` level badge (reuse `Badge`, `variant="neutral"`) | Opens the detail sheet with building name (`name_key`), `building.level`, `city.slot_category`, and — if a `Construction` order targets this slot — the existing `Timer` + `city.construction_finish` copy. No upgrade button in this phase (Phase 09 owns that CTA) |
| Under construction (occupied, has active order) | Same as Occupied, plus a small progress affordance (reuse `Timer`, not a new component) rendered inside the tile itself so the "living scene" reads at a glance without opening the sheet | Same sheet as Occupied, with the timer already visible |

Every slot is `accessibilityRole="button"` with a label from
`city.slot_accessible_empty` or `city.slot_accessible_occupied`.

### Detail sheet

Reuse `BottomSheet` exactly as `WorldTileDetailSheet.tsx` does — same
`snapPoints` formula (`${theme.spacing['3xl'] * 4}%`), same
`accessibilityViewIsModal` + `enablePanDownToClose` props. Unlike the world
map's sheet, this one needs **no loading/stale/error sub-states**: slot data is
already resident in the already-fetched `CityData` query (no per-tap network
call), so the sheet only ever renders its "ready" content — either the empty
branch or the occupied branch described above.

### Pull-to-refresh

Wrap the scene's outer container in a `ScrollView` with `RefreshControl`
(`tintColor={theme.color.accent.bronze}`, matching the loading-spinner
convention above), `contentContainerStyle={{ flexGrow: 1 }}`. This is the
standard RN idiom for enabling the pull gesture on a view that does not
naturally overflow — required because success criterion 3 explicitly demands
pull-to-refresh, and no screen in this codebase has needed it before now (there
is no existing `RefreshControl` usage to diverge from).

### State management

Follow the exact pattern `world` already established
(`docs/mobile/architecture.md` § The state rule):

- **Server state** (`CityData`, including the slot list) → TanStack Query,
  same `['game', 'city']` query key already in use.
- **Client state** (which slot's sheet is open) → a new, minimal Zustand store
  mirroring `cameraStore.ts`'s shape (`selectedSlot: string | null`,
  `selectSlot()`, `clearSelection()`). Do not add slot data to this store —
  only the identity of the selection, exactly like `cameraStore` only ever
  stores `selectedX`/`selectedY`, never tile contents.
- **Realtime** (Phase 07-04's `city.{id}` channel): patch or invalidate the
  `['game', 'city']` query cache on the relevant event, never write to a
  parallel store — same rule the map's delta application already follows.

## Data Contract Dependency (flagged for the planner, not decided here)

Roadmap success criterion 2 requires: *"A city exposes a fixed set of build
slots, each either empty or holding exactly one building."* Today's
`CityData.buildings` (see `packages/contracts/openapi.yaml` `CityBuilding`
schema and `CityStateService::handle()`) only returns **occupied** slots — a
5-row array for the starter city, with no representation of the empty ones.
This UI contract is written **against the following assumed shape**, which
07-01/07-02 must deliver before 07-03 can be built:

```yaml
CitySlot:
  type: object
  required: [slot, status]
  properties:
    slot:
      type: string
    status:
      type: string
      enum: [empty, occupied]
    building:
      oneOf:
        - $ref: '#/components/schemas/CityBuilding'
        - type: 'null'
```

`CityData.buildings` (array of `CityBuilding`) is replaced by
`CityData.slots` (array of `CitySlot`, fixed length, always returned in full).
This is a genuine open decision for the backend plan, not something a UI
researcher can settle — flagging it here so 07-02 and 07-03 land in the same
shape and 07-03 does not block on a schema surprise.

## Flagged Assumptions (autonomous mode — not blocking, confirm during planning)

1. **Slot detail sheet has no upgrade CTA in this phase.** Roadmap/CONTEXT.md
   defers "Building upgrades" to Phase 09. The currently-committed
   `city.tsx` already wires an `/upgrade` mutation (pre-existing MVP scaffold,
   see `apps/api/tests/Feature/Mvp/MvpGameplayTest.php`). This contract assumes
   that CTA is removed when the screen becomes a scene, and reappears properly
   in Phase 09-05. If the planner instead wants to keep upgrade wired through
   Phase 07, the sheet layout above still holds — just add a `Button
   variant="secondary"` row (never primary/bronze, per the Color section) below
   the level/category info, following `city.tsx`'s existing pattern.
2. **Total slot count is server-driven and unknown at spec time** (today 5,
   growing toward the 18 buildings `docs/game-design/buildings.md` documents).
   The grid algorithm above is deliberately count-agnostic; no fixed number is
   assumed anywhere in this contract.
3. **Background art (`city_ground.png`) generation is in this phase's scope**,
   not deferred to Phase 44, because roadmap criterion 3 already requires a
   rendered "scene." Phase 44 adds *ambience on top* (particles, weather,
   idle animation) — it does not introduce the base scenery for the first time.
   If the planner judges this out of budget for 07-03, the frame may ship on
   `bg.sunken` alone (no image) as a documented interim step, with the asset
   added in a follow-up plan — but it must not be a grey placeholder left
   silently unaddressed.
